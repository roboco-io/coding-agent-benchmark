# 모델·에이전트 조합별 바이브코딩 효율 실험 개선 제안

> 후속 상태(2026-09-21): 계측·판정 정정은 [정정 기록](2026-09-21-corrections.md)에 반영했다. 아래 내용은 당시 제안과 원인 분석 기록이다. 새 파일럿은 [EXP-024](../experiments/024-practical-combinations/README.md)에서 추적한다.

작성일: 2026-09-19 · 검토 기준: `303cf5b` 및 저장소에 보관된 원자료

우선 목표 확정(2026-09-20): 사용자는 **실무에서 쓸 모델·에이전트 조합 선택**을 선택했습니다. 작업 유형별 품질·예산 조건 아래 합격률·비용·시간·사람의 작업량을 비교하는 방향을 우선합니다. 아래 파일럿 규모는 제안이며, 실행 대상과 예산은 별도로 정합니다.

**가장 먼저 할 일은 기존 토큰 집계를 바로잡는 것입니다. 그다음에는 품질 기준을 만족하는 결과 한 건을 얻는 데 필요한 비용·시간·사람의 작업량으로 조합을 비교하는 방향을 권합니다.**

현재 프로젝트는 원자료 보관, 사전 가설 등록, 외부 채점, 실패 원인 기록을 갖추고 있습니다. 특히 EXP-007의 계측 오류 분석과 이후 채점기 개선은 다음 실험의 기반입니다. 다만 최근 실험의 주된 질문은 “이 조합이 RealWorld 백엔드를 완주하는가”입니다. 사용자가 처음 제시한 “조합에 따라 효율이 달라지는가”를 답하려면 평가 지표와 비교 설계를 확장해야 합니다.

이 문서는 개선 제안입니다. 기존 실험 보고서의 판정이나 집계 코드를 수정하지 않았으며, 새로운 모델 실행도 수행하지 않았습니다. 아래 재집계는 기존 로그를 읽어서 수행했습니다.

## 1. 최우선: 초기 실험의 계측 오류 정정

[`aggregate_tokens.py`](../scripts/aggregate_tokens.py)는 `message.usage`가 있는 모든 행을 합산하며 `message.id` 중복을 제거하지 않습니다. 초기 로그에는 같은 메시지의 동일한 usage가 여러 행에 반복됩니다. 이는 [EXP-007](../experiments/007-solar-open2-autopsy/report.md)이 이미 발견한 문제와 같은 형태입니다.

EXP-001~004의 저장된 `runs/*/logs/*.jsonl`을 재집계했습니다. 동일 run 안의 `message.id`를 한 번만 반영했으며, 확인한 중복 메시지의 usage는 모두 동일했습니다. 따라서 아래 차이는 중복된 usage 합산에서 발생합니다.

| 실험·조건 | 기존 집계 | 중복 제거 후 | 보고서 해석에 미치는 영향 |
|---|---:|---:|---|
| EXP-001 Ralph | 324,775 | 136,506 | PTE 비교의 기준값 변경 |
| EXP-001 PTE | 2,839,815 | 1,128,420 | Ralph 대비 8.7배 → 약 8.27배 |
| EXP-003 PTE + 스킬 | 1,723,575 | 875,083 | PTE 대비 절감률 39.3% → **22.45%** |
| EXP-004 skills-1 | 399,604 | 117,352 | 두 run의 차이가 크게 축소 |
| EXP-004 skills-2 | 198,819 | 118,311 | 범위 차이 200,785 → **959** |

수치는 기존 보고서의 `input + output + cache_creation` 정의를 그대로 사용한 토큰 대리지표입니다. 실제 청구 금액이 아니며, 보관된 로그 밖의 누락 요청·서브에이전트 비용까지 검증한 값도 아닙니다.

가장 큰 영향은 [EXP-003](../experiments/003-pte-skills/report.md)입니다. 사전 기준은 30% 이상 절감인데 재집계 결과는 22.45%이므로, 현재의 “S-02 검증” 판정은 그대로 유지할 수 없습니다. 스킬 효과가 없다고 단정할 수도 없습니다. n=1이고 테스트 정본과 태스크 분할도 함께 달라졌으므로, 관측된 절감과 그 원인의 불확실성을 구분해야 합니다.

[EXP-004](../experiments/004-ralph-skills/report.md)의 “동일 조건에서 약 두 배 변동”도 이 토큰 지표에서는 재현되지 않습니다. 다른 실험의 실제 변동까지 부정하는 결과는 아니지만, 이 사례를 근거로 삼은 README의 일반화는 재검토해야 합니다.

권장 작업은 다음 순서입니다.

1. 공통 집계기에 공급자·로그 형식별 중복 제거와 누계 처리 규칙을 명시합니다. usage 누락은 0과 구분합니다.
2. EXP-001~004 및 이 값을 인용한 문서·대시보드의 영향 범위를 재계산합니다. EXP-007 이후 보고서까지 일괄 오류로 취급하지 않습니다.
3. 기존 수치, 정정 수치, 변경 이유를 함께 남기고 가설 판정을 갱신합니다.
4. 중복 행, 누적 usage, reasoning의 output 포함 여부, 누락 usage를 검사하는 작은 회귀 테스트를 추가합니다.

## 2. 비교 목적을 명확히 정의

‘에이전트’를 CLI 제품과 워크플로 전략에 모두 사용하면 원인 해석이 모호해집니다. 다음 네 요소를 별도로 기록하는 편이 좋습니다.

| 요소 | 예시 | 비교에서의 역할 |
|---|---|---|
| 모델 | 모델 ID·리비전, 추론 설정 | 연구 대상 |
| 실행 도구 | Claude Code, Codex CLI와 버전 | 연구 대상 또는 고정 조건 |
| 작업 전략 | 단일 세션, Ralph, 계획 후 실행, 병렬 분할 | 연구 대상 또는 고정 조건 |
| 연결·환경 | 제공자, 변환 계층, 캐시, 글로벌 지침·MCP | 통제 변수 또는 별도 비교 대상 |

예를 들어 [EXP-011/012 비교](../experiments/012-ccr-gpt56-sol/report.md)에서는 실행 도구뿐 아니라 연결 계층과 장애도 달라집니다. 5분 46초 대 58분이라는 차이는 해당 전체 조합의 관측값으로 유용하지만, 실행 도구만의 효과로 해석하기는 어렵습니다.

| 방향 | 얻는 답 | 필요한 노력 | 제안 |
|---|---|---|---|
| 실무 조합 비교 | 내 작업에서 어떤 조합을 선택할 것인가 | 기존 구조 확장 | **우선 추진** |
| 요인 분리 실험 | 모델·도구·전략 중 무엇이 차이를 만드는가 | 공통 지원 조합의 교차 실험 필요 | 선별한 조합에 집중 |
| 공개 벤치마크 | 다른 환경에서도 같은 결과가 나오는가 | 실행 환경·과제·채점 배포 필요 | 앞의 두 단계 뒤에 확장 |

실무 비교에서는 각 제품의 권장 설정을 포함한 전체 조합을 평가할 수 있습니다. 원인 분리에서는 동일 모델을 지원하는 두 도구와 두 모델을 교차하여 네 조건을 모두 측정하고, 전략·연결 조건은 고정해야 합니다. 공통 지원 조합이 없으면 빈 셀을 임의로 채우거나 도구 효과를 추정하지 않습니다.

모델에 따라 어떤 도구가 유리한지가 달라지는지도 확인해야 합니다. 이것이 ‘모델 × 도구’ 상호작용입니다. 모든 조합을 관측하는 요인 설계와 시간대별 블록 설계가 출발점이 될 수 있습니다. [NIST 요인 설계](https://www.itl.nist.gov/div898/handbook/pri/section3/pri333.htm), [NIST 블록 설계](https://www.itl.nist.gov/div898/handbook/pri/section3/pri332.htm).

## 3. 효율을 품질·비용·시간으로 정의

모델 간 토큰 수는 토크나이저와 usage 정의가 다르므로 그 자체로 공통 효율 척도가 되기 어렵습니다. `billable`이라는 이름도 캐시 읽기를 제외한 현 지표의 의미를 정확히 전달하지 못합니다.

권장 핵심 지표는 다음과 같습니다.

| 지표 | 정의와 용도 |
|---|---|
| 예산 내 합격률 | 사전에 정한 시간·비용 한도 안에서 동일한 최종 채점을 통과한 비율 |
| 합격 한 건당 관측 비용 | 실패·재시도를 포함한 전체 실행 비용 ÷ 합격 건수. 합격 0건이면 유한 비용을 제시하지 않음 |
| 완료 시간 | 요청 시작부터 외부 검증 완료까지. 성공 run의 분포와 미완료·시간 초과 비율을 함께 표시 |
| 사람의 작업 시간 | 프롬프트 작성, 개입, 결과 검토, 수정에 쓴 실제 시간 |
| 품질 | 공개 테스트·숨긴 테스트·회귀·경계 조건의 통과 여부와 후속 변경 결과 |
| 진단 지표 | 호출 수, 세션 수, 캐시 사용량, reasoning, 도구 오류, 재작업량 |

비용은 공급자별 청구 의미를 확인해 비캐시 입력·캐시 읽기·캐시 쓰기·출력에 당시 단가를 적용합니다. reasoning이 output에 포함되면 중복 가산하지 않습니다. 도구·실행 인프라 비용도 별도 기록합니다. 구독 실행은 실제 지출·사용 한도와 API 단가 환산 추정치를 분리하며, 미측정을 무료로 간주하지 않습니다.

완료 시간만 비교하면 실패한 느린 run이 빠져 순위가 왜곡됩니다. 모든 run을 포함한 예산 내 합격률을 먼저 보고, 성공한 run의 비용·시간은 조건부 지표로 해석합니다. 합격 한 건당 비용도 미래 성공 비용의 확정 추정치가 아닌, 정해진 과제 묶음에서 관측한 비율입니다.

점수 하나로 합치기보다 품질 기준을 통과한 조합의 비용·시간 관계를 보여주고, 사용자의 작업 유형에 맞춰 선택하도록 권합니다. 정확도와 비용을 함께 평가하고 평가용 과제를 분리해야 한다는 방향은 [AI Agents That Matter](https://arxiv.org/abs/2407.01502)와도 부합합니다.

## 4. 과제를 늘려 차이가 드러나는 조건을 찾기

현재 RealWorld 과제는 최근 여러 조건이 첫 iteration에서 통과합니다. 이 조건에서는 Ralph의 반복 복구 능력이나 장기 작업의 컨텍스트 관리 차이를 관측하기 어렵습니다. RealWorld는 회귀 기준선으로 유지하면서 다음 과제를 추가하는 것을 권합니다.

| 과제 유형 | 확인할 차이 | 평가 방법 |
|---|---|---|
| 신규 구현 | 현재 결과와의 연속성 | 고정된 API 채점 |
| 기존 코드의 기능 추가 | 코드 이해와 변경 범위 관리 | 신규 요구사항 + 기존 회귀 테스트 |
| 버그 수정 | 탐색·진단·수정 효율 | 재현 테스트 + 관련 회귀 테스트 |
| 여러 단계의 요구 변경 | 컨텍스트 유지와 설계 변경 비용 | 단계별 독립 요구사항 및 누적 품질 |

가능하면 서로 다른 코드베이스를 포함하고, 최종 평가용 과제는 프롬프트·전략 조정에 사용하지 않습니다. 공개된 유명 과제는 사전 노출 가능성이 있으므로, 동일 명세의 새로운 변형이나 별도 과제에서 결과가 유지되는지 확인합니다. 현재 자료만으로 학습 데이터 오염이 있었다고 판단할 수는 없습니다.

최종 채점은 에이전트가 수정하거나 읽을 수 없는 환경에 둡니다. 개발용 테스트는 공개하되, 숨긴 테스트는 명세에 있는 동작만 검사해야 합니다. 문서·커밋·코드 줄 수는 품질 대리지표로 단정하지 말고, **후속 기능 변경 한 건에 드는 시간과 회귀 발생률**로 유지보수 가치를 확인하는 것이 좋습니다.

사람과 대화하면서 진행하는 바이브코딩까지 일반화하려면 별도 트랙이 필요합니다. 사용자가 실제로 소요한 검토·수정 시간을 측정하고, 동일인이 이미 푼 과제를 다시 풀어 얻는 학습 효과를 통제해야 합니다. 무개입 트랙과 사람 개입 트랙은 서로 다른 질문에 답합니다.

## 5. 반복 횟수·환경·실패 처리 개선

**n=3의 3/3 성공은 유용한 관측이지만 높은 성공률이 확정됐다는 뜻은 아닙니다.** 독립적이고 성공확률이 같은 세 번의 시도라고 가정해도, 이항분포의 양측 95% 정확 신뢰구간은 약 29.2~100%입니다. 하한은 `0.025**(1/3)`으로 계산됩니다. 같은 과제의 반복만으로 다른 과제까지 일반화할 수는 없습니다. [NIST 소표본 이항 신뢰구간](https://www.itl.nist.gov/div898/handbook/prc/section2/prc241.htm).

따라서 “재현성 확정”, “동급”, “원인은 캐시” 같은 문구는 근거 수준에 맞춰 “이 조건에서 3회 모두 성공”, “차이를 식별하지 못함”, “가능한 설명”으로 조정하는 것이 좋습니다. 관측 범위가 겹친다는 사실만으로 동등성을 증명할 수 없습니다.

실행 조건은 다음과 같이 정리할 수 있습니다.

- 같은 과제·가까운 실행 시간대를 블록으로 묶고 그 안에서 조합의 실행 순서를 무작위화합니다. 비교 기준선도 같은 시기에 다시 실행합니다.
- 모델 ID·가능한 리비전, CLI·채점기 버전, 프롬프트·설정·과제 커밋의 해시, 제공자, 도구 권한, 실제 노출된 지침·MCP를 보관합니다. 인증정보는 제외합니다.
- [EXP-023](../experiments/023-fable51-ralph/README.md)의 비격리 네이티브 조건과 격리된 서드파티 조건을 같은 통제 환경으로 취급하지 않습니다. 인증 제약이 있으면 전용 OS 사용자나 환경 스냅샷 등으로 노출 설정을 고정합니다.
- 새 작업 디렉터리·DB·세션으로 시작하고 캐시 조건을 기록합니다. 서버 캐시를 통제할 수 없다면 그 한계를 명시하고 실행 순서 효과를 확인합니다.
- iteration 수에 더해 시간·금액 한도를 설정합니다. 실제 실행은 iteration당 작업량이 다르므로 iteration만으로 자원 예산을 맞출 수 없습니다.
- 모델 실패, 도구·변환 계층 실패, 제공자 장애, 채점기 장애, 사람 개입을 구분합니다. 장애 run의 제외·재실행 규칙을 결과를 보기 전에 고정합니다.
- 실무 비교에서는 장애와 복구까지 전체 시간·비용에 반영합니다. 원인 분석용으로 장애 제외 결과를 제시할 때에도 전체 결과를 함께 공개합니다.

표본 수는 관행적으로 n=3이나 n=5로 정하기보다, 파일럿에서 얻은 변동과 실무적으로 의미 있는 차이로 정합니다. 예를 들어 비용 20% 절감이나 합격률 허용 차이를 사전에 정하고, 이에 필요한 과제 수와 반복 수를 산정합니다. 여러 과제에서는 과제를 분석 단위로 묶어 비교하고, 같은 과제의 여러 run을 서로 다른 과제처럼 세지 않습니다.

## 6. 권장 실행 순서

| 단계 | 구체적 작업 | 완료 기준 |
|---|---|---|
| P0: 계측 정리 | 초기 로그 재집계, 영향받은 판정·문서 정정, usage 규칙 통일 | 같은 원자료에서 같은 표를 재생성 |
| P1: 기준 환경 | 공통 runner·채점기·환경 manifest·실패 분류 정리 | 알려진 정답은 통과, 오답은 실패하며 모든 run의 환경 식별 가능 |
| P2: 실무 파일럿 | 후보 조합 2개 × 과제 4개 × 반복 3회 = **24회** | 합격률·비용·시간·실패 원인 및 변동 추정 |
| P3: 확증 실험 | 별도 평가 과제와 파일럿 기반 표본 수로 재검증 | 사전 정의한 실무적 차이와 불확실성을 함께 보고 |
| P4: 원인 분리 | 공통 지원 모델 2개 × 도구 2개, 전략 고정 | 모델·도구 효과 및 조합에 따른 차이를 구분 |

P2의 과제 4개는 유형별 1개씩 선정하는 작은 파일럿입니다. 일반적인 성능 순위를 확정하기에는 부족하며, 한 유형을 대표하는 여러 과제를 추가할 근거를 얻는 단계입니다. 사람 개입 비교는 무개입 파일럿 이후 별도로 설계합니다. 새 API 실행의 실제 예산과 대상 모델은 이 문서에서 확정하지 않습니다.

실험 관리 구조도 현재 규모에 맞출 수 있습니다. 공통 runner·채점기를 한곳에서 버전 관리하고 실험별 차이는 manifest에 기록합니다. 요청별 기록에서 run별 결과를 만들고, 이 데이터로 표·대시보드를 생성하면 보고서 문장을 다시 파싱하는 의존성을 줄일 수 있습니다. 요약 결론은 데이터와 구분하여 검토합니다. [HAL](https://hal.cs.princeton.edu/about)의 비용·실행 기록을 함께 추적하는 평가 구조는 참고할 만합니다.

빠르게 정리할 문서 불일치도 있습니다. [README 방법론](../README.ko.md)은 아직 “모든 실험은 Claude Opus 단일 모델”로 서술하고, [공통 과제](../tasks/realworld-backend/README.md)는 Postman/Newman을 완료 기준으로 적고 있습니다. 현재 실험의 모델 범위와 고정된 채점 정본을 반영해야 합니다. 실험 템플릿에도 환경 manifest, 예산, 제외 규칙, 불확실성, usage 출처 항목을 추가하는 것을 권합니다.

## 부록: 재집계 재현 코드

저장소 루트에서 실행하는 읽기 전용 Python 코드입니다. 이번 점검 범위인 EXP-001~004의 보관 로그를 대상으로 합니다. 서로 다른 usage가 같은 ID에 나타나면 중단하므로, 다른 공급자의 스트리밍·누적 로그에 그대로 적용하는 범용 집계기로 사용해서는 안 됩니다.

```python
import json
from pathlib import Path

fields = ("input_tokens", "output_tokens", "cache_creation_input_tokens")
for prefix in ("001-", "002-", "003-", "004-"):
    experiment, = Path("experiments").glob(prefix + "*")
    for directory in sorted((experiment / "runs").glob("*/logs")):
        seen = {}
        raw = duplicates = 0
        for log in sorted(directory.glob("*.jsonl")):
            for line in log.read_text().splitlines():
                event = json.loads(line)
                message = event.get("message")
                if not isinstance(message, dict):
                    continue
                usage = message.get("usage")
                if not usage:
                    continue
                message_id = message.get("id")
                assert message_id, (log, "missing message.id")
                raw += sum(usage.get(k, 0) or 0 for k in fields)
                if message_id in seen:
                    assert seen[message_id] == usage, (log, message_id)
                    duplicates += 1
                seen[message_id] = usage
        unique = sum(
            sum(usage.get(k, 0) or 0 for k in fields)
            for usage in seen.values()
        )
        print(experiment.name, directory.parent.name, raw, unique, duplicates)
```
