# EXP-043 이탈 기록

## D-1. 실행 중 run 상한 변경 (2026-10-10 17:23, 사용자 지시)

**변경 내용**: 사전 등록한 상한 `MAX_SEC=14400`(4시간)·`STALL_SEC=900`(정체 900초)을 `MAX_SEC=3600`(1시간)·`STALL_SEC=300`(정체 300초)으로 줄였다. 반복 상한 30 iteration은 유지했다. 같은 값을 아직 기동 전인 EXP-044에도 적용했다.

**변경 이유**: 사용자는 4시간 상한이 최근 결과에 맞지 않는다고 판단해 상한을 줄이라고 지시했다. 실험자는 최근 실험의 완주 소요 시간(run 시작부터 게이트 통과 iteration 종료까지)을 다음과 같이 확인했다.

| 실험 | 완주 run 소요(분) |
|---|---|
| EXP-035 agy gemini-3.8-flash | 18, 16, 23 |
| EXP-036 pi gemini-3.8-flash | 16, 14, 13 |
| EXP-037 claude-native haiku-5.5 | 8, 7, 5 |
| EXP-038 pi haiku-5.5 | 6, 6, 6 |
| EXP-040 agy gemini-3.1-pro | 18, 16 |
| EXP-042 claude-direct qwen (중단) | flash 14·12, q27 25, coder 123 |

coder 123분은 EXP-042 D-1의 제공자 usage 결함(입력 한도 초과 400 반복)이 늘린 값이다. 이를 빼면 최장 완주는 25분이다. 1시간은 그 2배 이상이다. 정체 300초는 정상 진행 중인 세션이 5분 동안 세션 기록·로그·앱 파일을 하나도 갱신하지 않는 경우가 드물다는 실험자의 판단이며, 이 실험에서 측정한 근거는 없다.

**oss-en-1 처리**: oss-en-1은 15:41:21에 시작해 변경 시점에 이미 약 100분이 지나 새 상한을 넘었다. 실험자는 실행 중이던 iteration 9의 에이전트 프로세스를 17:21에 종료했다(exit 137). 하네스가 iteration 9를 정상 채점했다(0/13). 이어서 iteration 10이 17:22:59에 기동된 직후 실험자가 driver를 종료하고 metrics에 `timeout,2026-10-10 17:23:00` 행을 추가했다. 따라서 iteration 10 세션 파일은 기동 직후 기록만 담는다. 1시간 시점(16:41) 기준으로 보면 iteration 6까지 완료되었고 그때까지 게이트 통과는 없었다. 4시간 상한 기준과 1시간 상한 기준 어느 쪽에서도 oss-en-1은 미완주다(9 iteration 모두 0/13).

**판정 영향**: 판정 기준(완주 수/3)은 바꾸지 않는다. 상한이 짧아졌으므로 "1시간 안에 완주하지 못함"은 "4시간 안에 완주할 수 없음"을 뜻하지 않는다. 보고서에서 이 차이를 명시한다. oss-en-2부터는 새 상한으로 실행한다.

## D-2. run 상한 추가 단축: 1시간 → 20분 (2026-10-10 17:25, 사용자 지시)

**변경 내용**: 사용자가 run 1회 상한을 20분으로 줄이라고 지시했다. `MAX_SEC`를 3600에서 1200으로 바꿨다. 정체 300초와 30 iteration 상한은 D-1 그대로다. EXP-044에도 같은 값을 적용했다.

**근거와 한계**: D-1 표의 정상 완주 run은 5–25분이었다. 20분 상한에서는 EXP-042 q27-en-1(25분)과 EXP-035 flash38-en-3(23분) 같은 run이 미완주로 판정되었을 것이다. 따라서 20분 안에 끝나지 않은 run은 "20분 안 완주 실패"로만 해석하며, 이전 실험(4시간 상한)의 완주율과 직접 비교하지 않는다.

**oss-en-2 처리**: oss-en-2는 17:23:00에 1시간 상한으로 시작했다. driver는 시작할 때 `bench.env`를 읽으므로 실행 중인 driver에는 새 값이 반영되지 않는다. 실험자는 외부 스크립트(`cap_enforce.sh`)로 17:43:00에 진행 중 iteration을 종료하고, 하네스 채점이 끝나면 driver를 멈춘 뒤 `timeout` 행을 추가하도록 했다. 20분 전에 게이트를 통과하면 스크립트는 아무것도 하지 않는다. oss-en-3부터는 driver가 새 값을 직접 적용한다.

**oss-en-1과의 차이**: oss-en-1은 약 100분을 실행했다. 20분 상한 기준으로 보면 iteration 3(16:01:15 종료, 0/13, 시작 후 19분 54초)까지가 상한 안의 결과다. 어느 기준에서도 oss-en-1은 미완주다.

## D-3. oss-en-2 상한 적용 실패: 20분 이후에도 60분까지 실행 (2026-10-10)

**사실**: `cap_enforce.sh`는 17:43:01에 진행 중 iteration 5를 종료했고(exit 137), 하네스가 iteration 5를 채점한 뒤 17:44:38에 metrics에 `timeout` 행을 추가했다. 그러나 driver는 멈추지 않았다. driver는 iteration 6부터 26까지 계속 실행했고, 메모리에 남아 있던 원래 상한(`MAX_SEC=3600`)에 따라 18:23:10에 스스로 종료했다. 그래서 `metrics-oss-en-2.csv`에는 `timeout` 행이 두 개 있다.

**원인(추정)**: 스크립트는 `pgrep -f "driver.sh oss-en-2"`가 반환한 PID 가운데 가장 작은 값을 driver 본체로 간주했다. 그러나 그 PID는 driver의 하위 셸이었고 본체가 아니었던 것으로 보인다. 이 판단은 결과에서 추론한 것이며 PID 관계는 기록하지 않았다.

**판정 영향**: 판정에는 첫 `timeout` 행(17:44:38) 이전의 iteration 1–5만 사용한다. 이 구간은 모두 0/13이다. 17:44:38 이후 iteration 6–26의 결과는 상한 밖 참고 자료다. 이 구간에서도 게이트 통과는 없었고, 최고 결과는 실행 요청 26건, 성공 파일 0개였다. 이 구간의 토큰 사용량은 실제로 과금되었으므로 usage 집계에는 포함하고, 상한 안의 값을 따로 표시한다.

**재발 방지**: 실행 중 driver에 상한을 바꿔 적용해야 할 때에는 run-all이 직접 띄운 driver PID(`pgrep -P <run-all PID>`)를 대상으로 한다. 더 나은 방법은 driver가 iteration마다 `bench.env`의 `MAX_SEC`를 다시 읽게 하는 것이다(스킬 개선 후보).
