## 분석: argon은 3.8-flash보다 느린가

**결론부터 말하면 3 run 기준으로는 느리다고 볼 근거가 없다.** 세션 시간 범위가 겹치고(12.2–16.2분 대 13.1–15.6분) 중앙값은 argon이 1분 짧다. 3 run의 모델 대기 합도 2,341초와 2,327초로 거의 같다. "더 느리다"는 인상은 1단계 run 1(16.2분)이 EXP-036의 세 run보다 길었던 데서 나왔는데, run 2·3은 각각 13.0분·12.2분이었다.

**다만 일하는 방식은 크게 다르다.** argon은 run당 호출 수가 3.8-flash의 약 절반(평균 57 대 111)인 대신 호출 한 번의 대기가 약 두 배다(중앙값 8.7초 대 4.5초). 호출 수가 적은 이유는 두 가지로 보인다. 첫째, 한 응답에 도구 호출을 더 많이 묶는다(응답당 1.13 대 0.99). 둘째, 응답당 output이 더 길다(중앙값 159 대 104 토큰). 반면 run 전체 output은 오히려 적어(3 run 합 97.6K 대 123.5K) 같은 결과를 더 적은 토큰으로 냈다. 호출이 적으니 대화 맥락도 덜 쌓여 프롬프트 중앙값이 33K로 3.8-flash의 50K보다 작았다.

**호출당 대기를 고정 지연과 생성 시간으로 나누면 차이의 대부분은 고정 지연이다.** 호출별 대기를 output 토큰 수에 선형 회귀하면(`analysis/gemini4-argon-slowdown/percall.py`) 절편(output이 0일 때의 대기, 응답 시작 전 지연과 하네스 처리 시간을 포함)은 argon 8.5초·3.8-flash 4.7초이고, output 1천 토큰당 증가분은 9.0초·6.3초다(R² 0.62·0.68). 프롬프트 크기를 함께 넣어도 절편 6.5초 대 3.5초, 1천 토큰당 8.9초 대 6.2초로 같은 방향이며, 프롬프트 1천 토큰당 증가분은 0.06초 대 0.02초로 작다. argon 호출 172건에 3.8-flash의 회귀식을 적용하면 모델 대기는 약 1,420초가 되어 실제 2,341초보다 약 920초 짧다. 그중 약 650초(70%)가 절편 차이, 약 260초(30%)가 생성 속도 차이다. 즉 argon은 호출 하나를 시작하는 데 더 오래 걸리고 토큰도 더 느리게 내지만, 호출 수를 절반으로 줄여 세션 전체 시간은 상쇄됐다.

**이 분석의 한계.** 대기 시간은 세션 기록 시각 차이로 잰 관측값이며, 네트워크·제공자 대기열·pi 처리 시간이 섞여 있어 모델 자체의 속도가 아니다. 두 실험은 9일 간격으로 실행됐으므로 Gemini API의 시간대별 부하 차이를 배제할 수 없다. 회귀의 설명력(R² 약 0.6)이 높지 않아 절편·기울기는 대략적인 분해로만 읽어야 한다. run 1이 길었던 이유를 따로 확인하지는 않았다(run 1의 호출당 대기 15.4초는 run 2의 15.7초와 비슷하고, 호출 수가 60회로 run 2의 46회보다 많았다).

## 모델 유지·노출 설정

- 3 run 모든 응답(172건)의 `model` 필드가 `gemini-4-argon`이었다. thinking level은 `high`(`thinking_level_change` 기록)였다. 오류 응답은 없었고 마지막 응답 1건을 뺀 모든 응답이 도구 호출로 끝났다.
- 모델 정의: pi 0.87.1 내장 목록에 이 모델이 없어 내장 `google/gemini-3.8-flash` 정의를 따른 사용자 정의 항목(`runs/pi-models.json`)으로 실행했다. maxTokens는 API 모델 목록 값 32,768을 썼다.
- 격리: `PI_CODING_AGENT_DIR` 전용, `-nc -ns -ne -np -na`로 상위 AGENTS.md/CLAUDE.md·스킬·확장 비노출. 에이전트 환경의 비밀값은 `GEMINI_API_KEY` 하나다(`PI_KEEP_ENV`).

## 이탈·특이 사항

- **D-1 환경변수 출력에 키 노출**: run 1·3에서 에이전트가 환경을 확인하려고 `env`를 실행해 `GEMINI_API_KEY` 값이 로컬 세션 기록에 1건씩 남았다(앱 코드·실행 로그에는 없음). 같은 출력에 하네스 경로(`PI_SESSION_FILE`, `PI_CODING_AGENT_DIR`)도 찍혔지만 에이전트가 하네스 파일이나 다른 run을 읽은 기록은 없다. 리포 보관본은 `redact_keys.py`로 2건을 마스킹했고, 보관된 `sessions.tar.gz` 안에서 키 값 직접 대조 0건을 확인했다. 노출 범위를 하나의 키로 줄인 하네스 설계(EXP-036 D-3 대응)가 의도대로 작동한 사례이며, 키를 에이전트 환경에 넣는 한 `env` 출력을 막을 수는 없다.
- **하네스 시도 경위**: agy 1.3.2·1.3.6은 API 키 경로에서 이 모델을 인식하지 못했고, 대화형 `/model` 메뉴에는 "Ultra and paid Pro plan subscribers" 전용으로 표시됐다(사용자 확인). pi 첫 smoke는 EXP-036 방식의 `GOOGLE_API_KEY` 매핑으로 "No API key found for google"이 나 `GEMINI_API_KEY`로 고쳤다. 모두 API 호출 전 실패로 비용은 없다. 세부는 `runs/phase0.md`.
- **단계 승인**: 1단계 승인 기록·점검 보고서는 `preflight-approved.stage1`·`preflight-report.stage1.md`로 보존했다.
